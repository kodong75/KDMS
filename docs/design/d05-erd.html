1. 읽는 법

  • 1장은 한눈에 보기다. 테이블을 묶음(적재·작업·검증 전환)별로 놓고 키 요약과 상태 코드값을 함께 보인다. 정식 ERD 표기는 아니다.
  • 2장은 논리 ERD 다. 엔터티를 한글 이름으로, 관계와 핵심 속성(식별자·외래 식별자·주요 속성)만 그렸다. 머리 오른쪽 글은 그 엔터티를 구현한 물리 테이블 이름이다.
  • 3·4장은 물리 ERD 다. 대상 PostgreSQL 의 kdms 스키마에 실제로 있는 테이블·컬럼·타입을 그대로 그렸다. 3장 작업·적재·동기화, 4장 검증·전환·기록.
  • IE(Information Engineering, 정보 공학) 표기. 선 끝 기호로 관계 차수를 읽는다: 두 줄 = 정확히 1, 원 + 한 줄 = 0 또는 1, 원 + 까마귀발 = 0 이상(N). 부모 쪽이 1, 자식(FK 를 가진 쪽)이 N 이다.
  • 실선 = 식별 관계(부모 PK 가 자식 PK 에 들어감: watermark, cutover_step), 점선 = 비식별 관계.
  • 물리 엔터티 박스: 머리 = 테이블 이름과 한글 이름, 구분선 위 = PK, 아래 = 나머지 컬럼. 왼쪽 표시 PK·FK·UK, 오른쪽 NN = NOT NULL(빈칸은 NULL 허용). (FK) 는 PK 이면서 FK 인 컬럼.
  • 4장의 점선 테두리 엔터티(job, job_table)는 3장 엔터티를 관계를 보이려고 다시 그린 것이다.
  • 컬럼 설명·기본값·CHECK·인덱스 전체는 docs/database.md §2 한 곳에 둔다. 이 그림은 그 문서와 같은 순서로 컬럼을 그렸다.

3. 상태 값 (CHECK)

  • job.status: SCHEMA_DONE → LOADING → SYNCING → CUTOVER → VERIFIED → DONE, 전환 단계가 실패하면 FAILED(다시 load·sync·cutover 가능). PLANNED 는 기본값이지만 지금 코드는 쓰지 않는다. kdms reset --yes 는 SCHEMA_DONE 으로 되돌린다.
  • job_table.status: PENDING → LOADING → LOADED, 구간이 실패하면 FAILED 뒤 다시 적재. 반영기는 LOADED 테이블의 변경만 적용한다.
  • load_chunk.status: PENDING → RUNNING → DONE | FAILED. 다시 적재하면 DONE 이 아닌 구간만 처음부터.
  • cutover_run.status: RUNNING · DONE · FAILED, cutover_step.status: 여기에 SKIPPED. change_log.op: c · u · d, verify_result.check_kind: count · sum · hash, verify_row_diff.side: missing · extra · diff, event_log.level: INFO · WARN · ERROR.
  • 상태 전이 그림과 명령별 허용 상태는 docs/database.md §3.

4. 원칙

  • 상태는 대상 PG 한 곳(kdms 스키마)에 둔다. 별도 파일·메시지 브로커가 없다.
  • 행 값(개인정보)·비밀번호를 남기는 컬럼은 없다. 예외는 change_log.payload 이며 반영하면 바로 지운다. verify_row_diff.pk 는 PK 값만, 테이블마다 앞 100건.
  • 정의를 바꾸면 새 버전 SQL 파일을 더하고, 앱이 시작할 때 차례로 적용한다(v1 1단계, v2 4단계, v3 5단계).
